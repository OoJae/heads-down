########## SEEKER-SMS-STACK ##########
SUMMARY: As of 2026-09-29 the Solana Mobile Stack (SMS) is actively maintained and changing quickly. MWA v2.2.0 / wallet-adapter-mobile 2.3.0 (Aug 17, 2026) added a Nostr-relay transport. The JS dapp side gained Transaction V1 (4 KB tx) support on Sep 15, and the Seed Vault SDK added V1 support on Sep 26. Seeker Connect (npm @solana-mobile/seeker-connect-wallet-standard 0.1.0, Sep 11) gives web apps a branded, direct connection to Seeker's built-in wallet, but it is web-only for now; React Native and Kotlin versions are listed as "planned". The official toolchain is `npx solana-mobile@latest` (CLI 0.5.0) with 13 templates, mostly Expo + @solana/kit + @wallet-ui/react-native-kit 4.3.0, plus one Kotlin/Compose template. The CLI also provides a device playground, a fakewallet and a localnet with adb forwarding. The Seeker Genesis Token (SGT) is the only per-device attestation primitive developers can use. I checked it on-chain: it is a Token-2022 group (GT22s89nU4iWFkNXj1Bw6uYhJJWDRPpShHt4Bk8f99Te) with 121,031 members minted out of a 1,000,000 max. Each SGT mint has mint, freeze, close and permanent-delegate authority held by GT2zuHVaZQYZSyQMgJPLzvkmyztfyXg2NJunqFp4p3A4. SGTs can move only between a user's own accounts (permissioned), so the SGT mint address, not the wallet, is the stable device identity. TEEPIN's hardware attestation and the Guardian network are real and in the bug-bounty scope, but there is no public attestation API. Only one Guardian (Solana Mobile) was active at TGE, so Guardians are mostly marketing and staking plumbing for now. MWA has no background signing and no session keys: every signature is a foreground Seed Vault approval (fingerprint plus double-tap). A high-frequency daily-habit app therefore needs its own delegated or session-key design, which is a real technical-depth opportunity. Scale: ~121K SGT-verified Seekers, 200K+ Saga+Seeker devices shipped, 85K+ weekly active wallets (Mar 2026), ~9K DAU in Season 2 campaigns (Jun 2026), 1,000+ dApp Store apps. SKR supply is 10.62B, with 5.02B in the stake vault (verified on-chain). Seeker moved to Android 16 in MR7 (Mar 2026), so Live Updates (lock-screen and status-bar-chip ongoing notifications) are available and almost no crypto app uses them. Primitives that are unique to Seeker and underused: on-chain (not server-side) SGT gating keyed by SGT mint, .skr names as a social and payments graph, the tactile double-tap signing as a ritual, SKR used as a medium of exchange (staking integrations do not count for the SKR prize), and dApp Store deep links for Seeker-to-Seeker referral loops.

Optional features are solana:signInWithSolana and solana:cloneAuthorization. solana:signTransactions is deprecated. authorize() takes identity {uri, icon, name}, chain (solana:mainnet|devnet|testnet), auth_token (silent reauthorization), addresses, features and sign_in_payload (SIWS in the same round-trip). sign_and_send options are min_context_slot, commitment, skip_preflight, max_retries and wait_for_commitment_to_send_next_transaction. get_capabilities returns max_transactions_per_request, max_messages_per_request and supported_transaction_versions. Sessions last only while the transport is up; persistence comes from caching auth_token and reauthorizing. - [verified] SGT is not strictly soulbound. The docs say it moves only between a user's own Seed Vault Wallet accounts on a permissioned basis, and the mint address stays the same. IMPLICATIONS_FOR_WINNING:
- Build native: Expo with @wallet-ui/react-native-kit and @solana/kit, or Kotlin/Compose. Start from `npx solana-mobile@latest create --template expo-kit-anchor` (or kotlin-compose-minimal) so the GitHub history shows real on-chain program work, not a WebView wrapper.
- Treat the SGT mint as the core identity primitive and verify it on-chain inside your own program: check the TokenGroupMember group GT22s89… and mint authority GT2zuH…, and key PDAs by SGT mint. This beats the standard server-side Helius check on innovation and on security review, and it gives a provable one-Seeker-one-account guarantee (anti-bot leaderboards, fair drops, one-device-one-vote). Handle permissioned SGT moves by always checking the current holder.
- Solve MWA's 'every action needs a foreground double-tap' problem on purpose. Pattern: one Seed Vault–signed 'Clock In' transaction per day or session authorizes a scoped, expiring session key (an ed25519 burner or a Keystore-backed P-256 key verified via the secp256r1 precompile). That key handles high-frequency in-app actions, and the Seed Vault is reserved for value-moving actions. This is deep, demo-able and on theme with 'Clock In'.
- Make the double-tap signature a deliberate ritual (the daily commit or check-in), then keep the loop alive with Android 16 Live Updates, home-screen widgets and notifications. Judges weight stickiness at 25%, and lock-screen or status-bar presence is a rare, visibly mobile-native feature.
- Show social proof using Seeker-only rails: .skr names instead of addresses (resolve with @onsol/tldparser), Seeker-to-Seeker invites via solanadappstore://details?id=… deep links, and SGT-verified leaderboards. This speaks directly to Akshay and Beeman (Solana Mobile) and the Seeker community.
- For the $10k SKR prize, use SKR as a medium of exchange or stake inside your own mechanic (escrowed commitments, forfeits, rewards, tipping by .skr) rather than Guardian staking, which is explicitly excluded. Reading a user's staked-SKR position as a reputation or tier multiplier (as Colony did) is a possible extra but carries eligibility risk.
- Mert (Helius) is a judge: using Helius getTokenAccountsByOwnerV2 for SGT checks and Helius webhooks or streaming for real-time pushes is both correct engineering and good optics. For the Ethelsec judges, show a server-issued single-use SIWS nonce, a DB UNIQUE constraint on SGT mint, auth tokens in expo-secure-store, assetlinks.json-verified dapp identity, and human-readable transaction previews.
- Record the demo on a physical Seeker: fingerprint plus double-tap signing, SGT verification and the .skr identity are the visual 'only on Seeker' moments. Plan dApp Store submission early; review takes 3–5 business days, and prizes require publishing within 30 days.
- Use the fresh 2026 capabilities for extra technical depth if relevant: Transaction V1 (4 KB) support landed in MWA JS on Sep 15 and in the Seed Vault SDK on Sep 26, 250 ms slots are live on mainnet, and the MWA Nostr transport is new. Any legitimate use of these signals being at the frontier.

IDEA_SEEDS:
- Clock In ritual app: each morning the user double-taps to sign one 'clock-in' transaction that opens a time-boxed on-chain session (PDA keyed by SGT mint) and authorizes a session key. A Live Update chip then tracks the streak or shift all day, with SKR escrowed and forfeited to a community pot if the user misses.
- SGT-native 'one Seeker, one voice' primitive: an on-chain program plus a mobile app for Seeker-only polls, prediction or commitment markets, or fair-launch raffles, where eligibility is verified in-program via Token-2022 group membership. It could double as a public good other Seeker apps call via CPI.
- Proof-of-presence with the camera and GPS: a Seeker user captures a 108 MP photo or location proof signed by a hardware-backed Android Keystore P-256 key, verified on-chain via the secp256r1 precompile and bound to their SGT. Useful for IRL quests, DePIN check-ins or event attendance, and it fits the grants language about sensors, location, cameras and real-time payments.
- Seeker-to-Seeker payments and social graph on .skr: tap or scan (Solana Pay NFC/QR) to pay alice.skr, split a bill, or accept a challenge. Friends lists are SGT-verified and invites go out via dApp Store deep links, which gives a native viral loop limited to real devices.
- Daily habit and accountability staking in SKR: commit SKR to a habit (steps via Android sensors, focus time, gym check-in via location). Proof comes from phone sensors, and the payout comes from the pool of people who missed. SKR serves as the stake currency, not Guardian staking.
- Anti-bot Seeker leaderboard game: a short daily mobile game (a 'shift') whose score submissions are signed by session keys delegated from a daily Seed Vault signature. The leaderboard is SGT-deduplicated on-chain, which solves the sybil problem Seeker Season quests have.
- ORE-matched angle: an SGT-gated 'fair mining' client, one rig per verified Seeker, where the daily clock-in double-tap commits the day's ORE deployment and Live Updates show round progress. ORE fit needs confirming with the ORE-focused research dimension.

THINGS_TO_AVOID:
- PWA or WebView wrappers (`solana-mobile webshell`) and web-only Seeker Connect as the main integration. The hackathon explicitly scores web ports poorly, and Seeker Connect has no React Native or Kotlin support yet.
- Client-side-only Seeker detection (Platform.constants.Model=='Seeker' / Build.MODEL) for anything that grants value. It is spoofable, and the docs and security judges will flag it. Also avoid SGT checks that verify a different address than the SIWS-signed one, or reusable nonces.
- Keying anti-sybil state by wallet address instead of SGT mint. SGTs can move between a user's own accounts, and zero-balance token accounts stay behind after a move.
- SKR staking dashboards or Guardian-delegation UIs aimed at the SKR prize, which excludes staking integrations. A staking sample (react-native-samples/skr-staking) and the official stake portal already exist.
- Features the Seed Vault Wallet now ships natively: USDC yield (Kamino Earn vault), DeFi portfolio tracking and basic send, receive or swap. Also avoid generic perps or memecoin terminals (Flash Trade, Titan and others already exist) and the 'AI agent on your Seeker' concept (SeekerClaw shipped Feb 2026).
- Designs that need many sequential wallet popups. MWA has no background signing and Seed Vault requires fingerprint plus double-tap each time. Batch into one transaction or use scoped session keys.
- Storing MWA auth_token in plain AsyncStorage (the default); use expo-secure-store. Also avoid skipping assetlinks.json and dapp identity setup, since wallets may warn or decline, which hurts UX polish.
- Relying on the TEEPIN or Guardian device-attestation API; no public API exists. Do not pitch a feature that depends on it.
