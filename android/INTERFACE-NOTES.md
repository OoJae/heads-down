# INTERFACE notes from the Android chain layer

`programs/heads-down/INTERFACE.md` fixes PDAs, account layouts, the signed-message preimages,
the `dig` format and error codes. It gives only one-line summaries for the other instructions.
The Android builders needed exact bytes, so this file records every choice made where the
contract was silent or inconsistent. Each item is proposed for the lead to fold into INTERFACE.md.

The machine-readable form of every layout below is
`android/core/chain/src/test/resources/ix_vectors.json`: args, account metas with role names,
and data bytes. The signed-message vectors are `android/core/keys/src/test/resources/vectors.json`.
Both are generated by the unit tests, and the tests fail if the committed file differs.

All integers are little-endian. `data[0]` is the INTERFACE tag.

## 1. Instruction data and account lists (not in INTERFACE)

### Common conventions

- **Authorization byte.** Instructions the wallet *or* the rig key may authorize (`arm_shift`,
  `break_shift`, `freeze_rig`) carry `auth u8` right after the tag: `0` = wallet (authority
  signs), `1` = P-256. The program branches on it explicitly rather than inferring the path
  from the data length or signer set.
- **P-256 tail** (auth = 1): `precompile_ix u8 | sig_index u8 | counter u64`. This is the same
  field order as a `dig` entry (`hb_ix, hb_sig_index, counter`). The program rebuilds the
  preimage from its own state plus these fields, hashes it, and compares the result with the
  precompile's 32-byte message (INTERFACE "Signed P-256 messages").
- **Wallet path accounts** are always `authority (signer, read-only) | rig (w)`, where
  `rig = [b"rig", authority]`. A P-256 path is `payer (signer, w) | rig (w) | instructions sysvar`.
- **Never in instruction data:** bumps, the Executor address, or anything the program must
  derive itself.

### Client-side validation (the program must re-check all of it)

- Plan: `split` 0..=15, `solo` 0..=10, `lease` 1..=3, `flags` only bit0, `split + solo >= 1`
  unless focus-only, `window_end > window_start`.
- Caps: `cap_round <= cap_shift <= cap_week`, and `caps_expiry_ts > 0`. The plan must fit:
  `plan_max_ev_cost <= cap_max_cost` and `dig_lamports <= cap_round`.

## 2. Gaps and proposals

1. **`rotate_key` (tag 4) layout.** INTERFACE says only "new p256_pubkey (+ optional new
   attestation)". The layout above reuses `register_rig`'s body. The clock-in adds it when the
   Rig exists but this install holds a different Keystore key (reinstall or new phone). Without
   it, every heartbeat would fail the pubkey check.
2. **Break reasons have no code for "unplugged" or "unlocked".** The phone maps them as:
   lifted → 1 pickup, screen-on and unlock → 2 screen_on, unplugged → 6 manual.
   *Proposal:* add `7 unplugged` and `8 unlocked` to `ShiftLog.break_reason`.
3. **Nothing tells the program a shift was Night or Day** (`ShiftLog.mode` 0/1/2). Focus-only
   is `plan_flags` bit0. *Proposal:* `plan_flags` bit1 = day shift. The client does not send
   it yet, because the program would reject unknown flag bits.
4. **`end_shift` carries no reason, and the Rig has no field for the last BREAK reason.**
   *Proposal:* keep the BREAK reason in the Rig (for example the `_pad` at @76) so `end_shift`
   can write `ShiftLog.break_reason`.
5. **The FREEZE preimage binds `shift_id`, even when no shift is running.** The phone signs the
   last `shift_id` it armed (0 before any). The program must build the FREEZE preimage with
   `rig.shift_id`, whatever the state.
6. **Name mismatch.** `docs/ORE.md` §3/§4 says `automation.fee == Config.crank_fee`, but
   INTERFACE says `automation.fee == config.executor_fee`. The client follows INTERFACE and
   sets ORE `automate.fee = Config.executor_fee` (@80).
7. **`plan_max_ev_cost` needs a market price.** INTERFACE says the client computes it at arm
   time from the market price. No price feed exists yet (Jupiter proxy), so the tile uses a
   fixed policy: plan 0.53 SOL/ORE (Steady at the ECONOMICS snapshot) under a wallet cap of
   0.67 SOL/ORE (Hunter). See `app/.../rig/ChainClockIn.kt` `ClockInPolicy`.
8. **ORE `max_production_cost`** is sent as `u64::MAX`. ORE does not enforce it, and it would
   compare the raw EMA, not the program's pot-adjusted `ema_ev`. If ORE later enforces it,
   setting it to `cap_max_cost` could block digs that the program's gate allows.

## 3. Clock-in transaction (one wallet approval)

```
[ComputeBudget limit+price]?  only if a priority fee is configured (0 by default)
[end_shift]?                  Rig state in {Armed, Down, Cooling, Broken}; uses the current rig.shift_id
[rotate_key]?                 Rig exists with a different p256 key
[ORE automate]?               see below; never for focus-only
[register_rig]?               Rig does not exist (guest, no attestation)
set_caps                      week, shift, round = dig_lamports, max_cost, expiry = now + 7 days
arm_shift (wallet)            window = [now, now + 8 h]
```

- A **Frozen** rig is refused on the phone (unfreezing needs a deliberate wallet action).
- **ORE automate:** `executor = Executor PDA`, strategy 2, `fee = Config.executor_fee`,
  `reload = 1`, per-tile `amount = dig_lamports / (split + solo)` (floored), and
  `deposit = max(0, cap_shift + ceil(cap_shift / dig_lamports) × executor_fee − automation.balance)`.
  It is skipped when the Automation already has those settings and enough balance.
- The worst case (every optional instruction present) fits one legacy packet. Measured: the
  4-instruction first clock-in plus a CU limit is 677 bytes as legacy and 679 as v0. The
  version follows MWA `get_capabilities`.
- After confirmation (`err == null` only), the phone re-reads the Rig: `shift_id` is
  authoritative, and the local counter is raised to `hb_counter`.

## 4. Heartbeat uplink (crank intake), not in INTERFACE

WebSocket, `wss` only, one JSON text frame per message, client to server. Incoming frames are
ignored.

```json
{"rig":"<base58>","counter":42,"shift_id":7,"round_id":422593,"lease_rounds":1,"sig":"<base64 r||s, low-S>"}
{"kind":"break","rig":"<base58>","counter":44,"shift_id":7,"reason":1,"sig":"<base64>"}
{"kind":"freeze","rig":"<base58>","counter":46,"shift_id":7,"reason":3,"sig":"<base64>"}
```

- u64 values are exact, unquoted JSON numbers. A JavaScript intake must parse them as
  BigInt. The Rust crank can use `u64` directly.
- A heartbeat has exactly the six fields in the task contract. BREAK/FREEZE carry `kind`, so
  they can never be parsed as heartbeats. PLAN is never sent over the uplink.
- The crank reads `Rig.p256_pubkey` from the chain. The message carries no key.
- If the phone is offline, it queues at most 8 messages and flushes them on reconnect, but only
  while they are still useful: a heartbeat within `lease_rounds × 78 s`, BREAK/FREEZE within
  10 minutes.
- No authentication yet (SIWS session per THREAT_MODEL is future work). Forged frames gain
  nothing, because every message is P-256-signed and verified on-chain. An unauthenticated
  intake can be flooded, which affects liveness only.
